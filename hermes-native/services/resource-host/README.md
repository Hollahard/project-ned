# Windows resource ownership foundation

This Rust library is an isolated M1 feasibility slice for the Hermes native architecture. It does not start Hermes or Tabby, load a model, expose an IPC endpoint, or modify the existing Friday supervisor. It is not yet the durable per-user resource coordinator.

`WorkerGroup` owns an unnamed, non-inheritable Windows Job Object with kill-on-close. Each child starts suspended, is assigned to that job, and only then resumes. Assignment/resume failure cleans up that newly created process. A lifecycle mutex serializes spawning against permanent retirement, so a concurrent or later spawn cannot escape a completed termination. Restart requires a new group. Separate groups keep gateway/agent and inference lifetimes independent.

`WorkerSpec` requires an absolute existing executable and directory, literal argument values and an explicit environment map. The launcher uses `CreateProcessW` with an explicit application path, `CREATE_SUSPENDED`, `CREATE_NO_WINDOW` and `CREATE_UNICODE_ENVIRONMENT`. It does not inherit environment variables, invoke a shell, search PATH, discover listeners or kill processes by PID. Ordinary `spawn` inherits no handles. Captured launches inherit exactly their three standard handles through `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`. Values have no `Debug` implementation. Environment names must use the ASCII alphanumeric/underscore subset, with no case duplicates; the caller supplies every required Windows/runtime variable deliberately.

`Worker` retains a stable process handle for bounded exit observation. `terminate()` starts termination only for the group's owned tree and permanently closes its admission. `wait_timeout()` and `active_count()` observe completion. Neither operation proves VRAM release. Killing a job is an escalation after cooperative cancellation/unload, not a substitute for saving session state.

`contains_observed_pid(pid)` is a read-only membership snapshot for a PID returned by a trusted operating-system observation, such as the exact established TCP socket query in [owned-http](../owned-http/README.md). It opens only a non-inheritable `PROCESS_QUERY_LIMITED_INFORMATION` handle, tests that handle against this exact Job and closes it. It never adopts or terminates the PID. It rejects zero, inaccessible processes, unrelated processes, a busy lifecycle fence and retirement already requested. Descendant membership is valid; the observed server need not be the original root. This snapshot does not authenticate code or freeze concurrent retirement.

## Captured backend process API

`spawn_captured(&WorkerSpec, CaptureLimits)` supplies closed NUL stdin and continuously drains stdout/stderr from exclusive reader threads. It starts these readers before child execution. Only NUL/stdout/stderr child handles are inherited; parent readers, the Job, and unrelated inheritable handles are excluded. The original create-suspended, assign, resume sequence and failure guard remain shared by both launch modes.

`CapturedWorker::wait_ready(timeout)` recognizes only complete `HERMES_BACKEND_READY port=N` or `HERMES_DASHBOARD_READY port=N` records. LF/CRLF and fragmented reads are supported. Malformed records, conflicting ports, premature EOF, a dead root process, overlong lines and the total stdout bound fail explicitly. Bounds default to 16 KiB per line and 2 MiB total stdout, including output after readiness. A later conflict or exceeded bound invalidates prior readiness; callers must continue checking `readiness()` while bootstrapping. This parser does not prove listener ownership or authenticated identity.

The drainer continues consuming both streams even after readiness failure. It uses `PeekNamedPipe` and reads no more than the available buffered bytes, avoiding synchronous waits on an incomplete line. Raw output retention defaults to zero; counters and EOF status remain observable. Optional tails are capped at 1 MiB per stream, have no `Debug` implementation, and require caller redaction before logging. Stderr volume cannot block stdout readiness merely because a child fills its error pipe.

`finish_capture(timeout)` requires root exit, actual EOF on both pipes, and completed drainers. A descendant retaining a writer is not mistaken for cleanup success. `WorkerGroup::retire_captured(worker, code, timeout)` verifies ownership, permanently closes admission, terminates only that Job, and additionally requires zero active Job members. Bounded `terminate_timeout` closes admission before waiting for the spawn fence; timeout means cleanup is incomplete and the caller must retry or drop the owning group. An in-flight spawn may have committed to resume before retirement is requested, so timeout is never reported as successful cleanup. Kernel calls have no hard real-time scheduling guarantee.

Dropping a capture requests reader cancellation without waiting for child cooperation or joining threads. Reader threads own their handles/state and leave the polling loop on cancellation. Dropping a capture does not retire its resource family; use explicit retirement for verified cleanup. Dropping the last Job handle remains kill-on-close containment.

## Optional framed control-worker transport

`spawn_framed(&WorkerSpec, FrameLimits)` opts into a separate LF-delimited UTF-8 transport. It returns `FramedWorker` with `write_frame(payload_without_lf, timeout)`, `recv_frame(timeout)`, `close_stdin()` and `capture()`. `capture()` exposes the ordinary process handle/exit and output-EOF observations and is accepted by `retire_captured`. Port readiness parsing is disabled for this mode: the caller validates the application hello, protocol version, response IDs, JSON shape and authorized methods. No service or model is launched by the library itself.

Frames default to a maximum of 65,536 bytes including LF, with at most eight completed output frames queued plus one bounded partial frame. Hard bounds cannot be increased above those values. Invalid UTF-8, CR, empty frames, overlong frames, incomplete EOF and queue overflow invalidate the output stream and discard queued messages. Output continues to drain after failure. Raw stdout/stderr tails remain disabled. Completed final responses can still be retrieved after root exit; cleanup success is separate from application/protocol success. A receive timeout alone does not consume a response or resolve an outstanding request, so callers must correlate IDs and must not retry uncertain commands.

Framed stdin uses a private named byte pipe in `PIPE_NOWAIT` mode. The server writer is non-inheritable; only its client read handle enters the exact child handle list. A cryptographically random name, first-instance flag, one allowed instance, remote-client rejection, and verification that the connecting client is this parent process guard setup before child creation. The client uses normal blocking stdin reads. Writes make bounded progress or return at the deadline when the child stops reading. A partial-write timeout or I/O/protocol error closes input permanently; subsequent writes fail and callers must retire the owned group before replacement. Local payload-validation errors happen before writing and leave the stream usable.

`write_frame` success means bytes entered the kernel pipe, not that a request ran. Await the correlated application response. `close_stdin` and destructors never call `FlushFileBuffers`, because it can wait for the peer to read. Closing input does not promise delivery of unread bytes; graceful shutdown needs the application acknowledgment first. This is deliberately bounded synchronous polling, not an overlapped I/O engine or an interactive terminal. [Microsoft documents nonblocking byte-pipe partial writes](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-type-read-and-wait-modes) and the [blocking flush behavior](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-operations).

## Verification

Activate the development environment, then run from the repository root:

```powershell
. 'G:\Project_Ned\.venv\Scripts\Activate.ps1'
cargo test --manifest-path hermes-native/services/resource-host/Cargo.toml --locked --features test-fixture --quiet > "$env:TEMP\hermes-resource-test.log" 2>&1
cargo fmt --manifest-path hermes-native/services/resource-host/Cargo.toml --check
cargo clippy --manifest-path hermes-native/services/resource-host/Cargo.toml --locked --features test-fixture --all-targets -- -D warnings
```

The **28 tests** use only the crate's harmless fixture executables and parser inputs. In addition to the original eight ownership tests, they cover fragmented/bounded readiness, malformed/conflicting ports, closed stdin, exact handle inheritance, a 4 MiB stderr flood with bounded retained tails, early exit, readiness timeout, descendant-held pipe EOF, unrelated process survival, wrong-group rejection, and a retirement deadline expiring while the spawn fence is held. Framed tests cover Unicode and exact maximum-size round trips, real blocked-reader partial-write timeout, permanently closed input after uncertainty, output queue/encoding/size/EOF failures, a final reply after root exit, local validation, bounded receive waits and reader cancellation without child cooperation. The fixture binary is excluded from normal builds unless `test-fixture` is enabled.

Windows sandbox execution initially rejected suspended process creation with `ERROR_ACCESS_DENIED`. The same isolated tests passed under scoped unsandboxed execution; no installed application was launched or stopped. Formatter and Clippy checks passed with warnings denied. Additional Windows-created helper processes can be included in a job, so tests assert at least the expected child/descendant rather than an exact process count.

## Remaining integration gates

The production coordinator still needs a user-scoped singleton, authenticated IPC and permissions, persistent Gaming policy, runtime/process generations, a complete GPU producer registry, cooperative cancellation, telemetry and measured teardown deadlines. This library provides ownership, captured readiness, and bounded opaque-frame primitives; the separate terminal-host spike handles ConPTY I/O. It has no listener/socket ownership verification, backend HTTP client, application model-control protocol, or actual Hermes/Tabby launch integration. Worker specifications come from trusted coordinator code and are not a renderer-facing arbitrary-execution API. OS sandboxing of hostile child code is a separate boundary: a Job Object controls lifetime and membership, not file/network access.
